### Added
- **The audit log now answers the question a forensic investigator actually asks: what was this agent allowed to do at the time?** Most agent stacks resolve permission at call time and never persist it, so afterwards nobody can say. FerrumDeck has a policy plane in the path of every tool call, which makes it one of the few places that *can* answer — but only if the answer is written down at decision time. It was not: the entire record of "permissions available during the run" was a single boolean, `details.budget_headroom`.

  Every decision now carries a `permissions` block: the identity the decision was made *for* (tenant, project, agent, agent version, run, and the API key id that presented the call — never a secret), the budget remaining as **quantities** rather than a boolean, and a SHA-256 content hash of the policy document that produced it. The document — canonical allowlist, budget caps, enforcement mode — is stored once in the new content-addressed `policy_documents` table, immutable by trigger because the key *is* the hash of the value.

  The hash rather than the document, for two reasons. An allowlist is unbounded and identical across millions of decisions, so inlining it costs bytes and adds nothing. More importantly the hash sits **inside** the audit row and is therefore covered by that row's `record_hash` and the per-tenant chain: editing the allowlist a decision was made under leaves either a hash that resolves to nothing or a broken chain. An inline copy would be one more mutable blob.

  The invariant — *given only the audit log and the policy map, reconstruct what this identity was permitted to do at time T* — is asserted by an integration test against a real database, across a policy change, which is the case that matters: an agent permitted to write on Monday and not on Tuesday. A reconstruction that answers "what is it allowed now" is worthless and looks identical to a correct one until the moment it is needed. The reconstruction ships as `PoliciesRepo::reconstruct_permissions_at`, not as test-only code, because a capability only a test can perform is not a capability an investigator has; its SQL reads `audit_events` and `policy_documents` and names neither `agents` nor `runs`, so the answer survives the agent being deleted or re-permissioned.

- **[`docs/compliance/safe-evidence-coverage.md`](docs/compliance/safe-evidence-coverage.md): the eight SAFE evidence classes against what this repository records, one row each, with the schema location and a status.** SAFE (Shared AI Findings Exchange, Open Secure AI Alliance RFC, 2026-08-04) asks members to preserve specific evidence for a forensic response. Each verdict was checked against a running stack, not read off the source — and where the answer was "the column exists", the follow-up was "is anything ever written to it?". Three times it was not. Three classes moved MISSING → CONFORMS in this release; the other five are stated as they are, including two that are MISSING and stay MISSING.

- **A live-stack CI job that gates on tests which actually EXECUTED** ([#6](https://github.com/sattyamjjain/ferrumdeck/issues/6)). `tests/security`, `tests/chaos` and `tests/e2e` reported *135 collected, 135 skipped, 0 run*: chaos and e2e were in no workflow at all, security ran only inside a `|| true` step with no gateway behind it. All three were green and none had asserted anything. The new `live-stack-tests` job boots Postgres, Redis and the gateway, runs the three suites, and `scripts/check_live_stack_results.py` fails on any of: executed below a floor (a **cliff detector**, following the collection-floor precedent — the failure it guards collapses the count to ~0), a failure not declared in `.live-stack-known-failures.yml`, or a declared failure that has started passing, so the exemption list can only shrink. Each of the 16 declared entries carries a real diagnosis; an exemption without one is a silenced test.

- **A CRA paragraph in the README.** EU Cyber Resilience Act Article 14 reporting begins 2026-09-11 (24-hour early warning, 72-hour notification, 14-day final report, via the ENISA Single Reporting Platform). Those windows are short enough that the evidence has to exist before the clock starts, which is what the audit log is for — stated alongside the equally plain fact that FerrumDeck files nothing, notifies nobody, and is not a compliance product.

### Fixed
- **An escalated tool call was recorded in the audit trail as an allowed one.** The audit action was derived from the raw allowlist verdict rather than the effective decision, so when the reversibility ladder escalated `Allow` → `RequiresApproval`, `decision.is_allowed()` was still true and the row was written as `policy.allowed`. `details.effective_decision` held the truth, but `action` is the indexed, filtered, human-read field, and it said the opposite of what happened. `policy.approval_required` had consequently **never been written** since the constant was introduced. Now derived from the effective decision.

- **The human-approval control could not be reached, and its timeout was never recorded.** `PoliciesRepo::create_approval` had no callers and there is no `POST /approvals` route, so `approval_requests` was empty in every deployment, `GET /approvals` always returned `[]`, and the two resolution handlers — which are correct and do carry the approver — were unreachable. `approval.expired` was declared in the first schema and has never been written: both auto-expiry paths resolved the row and logged nothing, so the trail could not distinguish "expired" from "never happened". Both paths that park a run in `WaitingApproval` now open a real gate (policy-decision row, approval row, and `policy.approval_required` carrying the deadline), the expiry paths write `approval.expired`, and approve/deny/expire share one event builder carrying the resolving identity and `latency_ms`. Adding the expiry event *without* wiring creation would have been the same defect this repository keeps finding — code that exists and never runs.

  Latency is not decoration: an approval that took 40 minutes and one that took 4 seconds are different facts about the control, and only one of them is a control that works under load.

- **Every tool on the demo agent's own allowlist required human approval.** The dev seed registers four tools without a `reversibility`, so they inherited the column default `irreversible` — correct as a deny-by-default for an unassessed tool, wrong for `git_read`. Consequence: on a freshly seeded stack the R3 rung gated *every* call, the allow path was undemonstrable, the ladder looked like a blanket gate rather than a graduated one, and several security and chaos tests were failing against a correctly-functioning engine. Migration `20260819000002` classifies them (`git_read`/`test_run` reversible, `git_write` costly, `github_create_pr` deliberately left irreversible so the R3 gate still has something to demonstrate).

- **The live-stack suites were calling the wrong service.** 144 assertions across `tests/security` and `tests/e2e` addressed `/api/v1/...` — the Next.js BFF — while pointed at the gateway on :8080, which serves `/v1/...`. Every one 404'd. Many then passed anyway, because assertions like `assert status in (403, 404)` hold for a 404, and others took a `pytest.skip` branch: the same "green without asserting" shape as the readiness-probe bug fixed in 0.8.7, which had already documented this exact distinction in `tests/security/conftest.py` without the call sites being corrected. Also fixed: `POST /v1/workflows` requires a `project_id` that no test payload supplied, and the two multi-tenant fixtures now skip when their (deliberately unseeded) keys are not provisioned, instead of failing on the resulting 401 — which the conftest already said they should do.

### Changed
- **Approval deadlines are configurable** via `FERRUMDECK_APPROVAL_TTL_SECS` (default 3600). The deadline is recorded on the escalation event, so a reader can tell an approval that expired against a 60-second window from one that expired against a day-long one.

### Known gaps
Found while checking, recorded rather than fixed — each is a posture decision, not a bug fix. Full detail in [`docs/compliance/safe-evidence-coverage.md`](docs/compliance/safe-evidence-coverage.md).

- **Airlock's anti-RCE layer is name-matched and matches nothing on a seeded stack.** `RceConfig::target_tools` defaults to eight literal names (`bash`, `shell`, `python_repl`, …); the seeded tools are `git_read`/`git_write`/`test_run`/`github_create_pr`, so Layer 1 inspects nothing there and an RCE payload to `git_write` is authorized with `risk_score: 0`. A deployment that names its shell tool `run_cmd` gets no anti-RCE inspection and no warning that it is getting none. Widening the default trades false negatives for false positives and latency on every call.
- **Concurrent audit writes to one tenant collide and the loser is dropped.** `AuditRepo::create` reads the chain tip and inserts `tip + 1`; two concurrent writes pick the same sequence and one hits `idx_audit_events_chain`. Because audit writes are fire-and-forget, the loser is logged at WARN and the event is lost. The chain stays valid — it simply never contained the record. A chain that verifies is not a chain that is complete, and the log is lossy exactly when the system is busiest.
- **A NUL byte in a tool name reaches Postgres** and returns 500 (SQLSTATE 22021) rather than a clean deny.

### Added
- **The stub gate: the last surface the "exists but never executed" sweep had not covered.** Three gates closed that class in this cycle — a declared eval with no committed report, a collection root CI silently stopped matching, a suite no workflow could reach — and all three live in the `python-test` job. The HTTP surface was still ungated, and [#7](https://github.com/sattyamjjain/ferrumdeck/issues/7) named it directly: a route answering `200 {"suites": []}` is the same defect as an eval that never runs. It looks green and asserts nothing.

  `scripts/check_route_backing.py` audits all 47 BFF routes against `.route-backing.yml` and is a prerequisite of `ci-check`, beside the other three. The invariant it enforces is one both planes already followed, now written down so it cannot erode: **an unimplemented route returns 501 with an `issue:` link, never a fixture or an empty 200.** `200 {"total_regressions": 0}` reads as "we looked and found none"; 501 says "we never looked", which is the true statement.

  It fails on five distinct regressions, each with a test in `tests/test_route_backing.py`: a route reaching no backend; a declared stub that quietly became a fixture; a 501 citing no issue (an untracked stub is a permanent one); an honest stub nobody declared, so the stub surface stays countable; and a declaration gone stale after its route was implemented — which is what stops the file rotting into a permanent allowlist, the failure mode of every suppression list that only grows. The declaration format follows `.agent-audit-kit.yml`: minimal, per-entry, every entry carrying a rationale.

  **The audit found no fabrication.** 40 routes proxy the gateway, 4 are locally backed and declared with what they actually read (`health` reports on this process; the two `docker/*` routes spawn real `docker ps`/`docker logs`; `evals/suites` parses the on-disk YAML), and 3 are declared stubs — all three on #7. The gate does not fix a lie; it stops the honest-501 convention decaying into one. The gateway plane is held to the same rule — its one `NOT_IMPLEMENTED` site (`NO_EVAL_STORE` in `handlers/evals.rs`) is checked for an issue link too, so the invariant is not BFF-only.

- **A "Reproduce every number on this page" section near the top of the README.** `make reproduce-readme-figures`, `make reproduce-readme-figures-fast`, `make reproduce-spend-gate` and `make bench-enforcement` in one table with what each verifies and measured wall-clock (~70s / ~10s / ~50s / ~2.5 min cold), the reference machine stated where it matters, and the reason rates are compared exactly while latencies are banded: the rate benchmarks are seeded, offline and LLM-free, so a rate that moves at all is a behaviour change, whereas latency is a measurement of a busy machine whose p95 variance reached 4.4x under load. That distinction previously existed only in this changelog.

### Fixed

- **A hard gate on the "exists but never executed" class, and a fourth instance found while building it.** Three separate instances landed below — a suite declared and never scheduled, 18 test files CI never collected, a generated page built from gitignored files. Each was fixed individually; the class stayed open. Four gates now close it, all in the `python-test` job beside the tests and all prerequisites of `ci-check`, following the `eval-health-check` precedent — a gate someone can route around is a lint.

  `scripts/gen_eval_health.py` now **exits non-zero** when a declared eval has zero committed reports, instead of rendering it as a NEVER RUN row. The distinction it now draws is between a result and the absence of one: *never passed* means the eval runs and fails, which is evidence and belongs on the page; *never run* means nothing has ever executed it, which is not a result at all. `regression` sat at NEVER RUN for months while the page faithfully said so and nothing failed. Suites are discovered from `evals/suites/` as well as the hand-maintained `EXPECTED_EVALS`, so a new suite file is covered without anyone remembering to list it.

  `ci.yml` asserts the unit-test collection did not shrink, two ways: every collection root must yield at least one test (catching a path renamed or dropped), and the total must clear a floor of 520 against 550 today (catching a root that still resolves but stops matching). The floor is a cliff detector, not a ratchet — the failure it guards removes tens of tests at once. The root-level glob is counted as one group, as the test step passes it, because iterating its expansion trips over `tests/__init__.py`.

  `scripts/check_suite_reachability.py` fails if a suite under `evals/suites/` cannot be reached from any workflow trigger. It resolves three routes — a literal `--suite`, a shell variable assigned a literal in the same workflow (how `evals.yml` selects off `github.event.schedule`), and `make <target>` followed one level into the Makefile. That third route is why it reads every workflow rather than just the nightly: `asb` and `injection_defense` are gated from `ci.yml` via `make eval-injection-defense && make eval-asb`, a deliberate split, and diffing against the nightly alone would report the two most rigorous suites as unreachable.

- **One command re-verifies every numbered claim in README.md.** `make reproduce-readme-figures` drives the criterion latency sweep and the three offline rate benchmarks, then compares each against the published figure and exits non-zero on drift. `make reproduce-spend-gate` had this property for the two spend figures and was the only thing that did; the latency table, the block/benign rates and their Wilson intervals were hand-typed from a run nobody could re-run on demand.

  Two comparison regimes, because they are not the same kind of number. Rates (`17/17`, `8/8`, `13/13`, `6/6`, `4/4`) and their Wilson bounds are compared **exactly** — those benchmarks are seeded, offline and LLM-free, so any movement is a behaviour change. Latencies get a **band against a stated machine**: README says Apple M4 `--release`, and off that silicon the absolute nanoseconds are a different quantity, so the band widens and the output says which regime is in force. Bands are set from measured variance, not taste — two consecutive runs here under load gave the same case 1.03x and 1.35x, with a p95 spike to 4.4x, and `docs/benchmarks/enforcement-latency.md` independently records 2-5x under heavier load. p95 therefore gets a looser band than p50. Every row prints its ratio even when passing, so a figure drifting toward its band is visible before it crosses. A separate check asserts the README still literally contains the figures being verified, so a number cannot drift by being edited in the docs while every benchmark stays green.

  Wired into the nightly rather than per-PR (the criterion sweep is six cases at 100 samples), as a service-free job needing no Postgres, Redis or model credentials. On drift it opens or refreshes a single tracking issue **and** fails the job: an alert nobody is paged by and a status nobody reads are the same silence in different clothes.

### Fixed
- **`make bench-enforcement` had been failing outright, and it is the command README names for reproducing the latency table.** `scripts/bench-enforcement.sh` invoked `cargo bench -p fd-policy`; the crate's package name became `ferrumdeck-policy` when it was renamed for crates.io, and only its *lib target* is `fd_policy`. So the script exited 101 with `package ID specification 'fd-policy' did not match any packages` for anyone who ran it, which means the four published latency figures have had no working reproduce path since the rename. Found by work item 3 trying to build on it. ### Changed
- Worked out whether the failing evals are a broken harness or a real zero, and wrote the answer down instead of refreshing the page that reports it. Converted the security, chaos and e2e headline cases from liveness checks to behaviour checks.

  The answer is the third option, and it had been hidden twice in opposite directions. `evals/datasets/safe-pr-agent/tasks.jsonl` expects files changed, a pull request opened and tests passing against `example/project`, a repository that does not exist and that this control plane never clones. So the eval was measuring something the agent was never built to do, unsatisfiable by construction from the day the dataset was written. That first read as 0% ([#31](https://github.com/sattyamjjain/ferrumdeck/issues/31)), when the suite's declared scorers were discarded and substituted ones scored against run fields the runner never populates. After that fix it read as a clean 1.00, because the replacements mostly skip and a skip returned a full score: **exactly half of every committed report's scorer results were vacuous** (40 of 80 on each regression run, 3 of 6 on each smoke run). Neither number was ever evidence about the agent.

  The fix makes a skip a distinct outcome rather than a silent 1.0. `ScorerResult.skipped` is now a first-class field, `CompositeScorer` excludes skips from the weighted average and reports assertion coverage, and a task where every scorer skipped is reported unscored rather than passed. `EvalRunSummary.assertion_coverage` is emitted on every report. A new `LoadedSuite.unasserted_expectations()` names the dataset expectation keys that no declared scorer reads, which is the general form of the bug: a future dataset that quietly stops being tested now says so instead of averaging past it.

  Both suites were rescoped rather than tuned. `schema_valid` is removed, because no task declares an `output_schema` and it therefore skipped on every task of every run. `expected_output_match` is given a non-degeneracy floor it can actually check. `require_all_scorers_pass` is set so a half-failing task stops reporting as passed. Assertion coverage goes from 50% to 100% on both suites, and a degenerate response now fails where it previously scored 1.00. `docs/eval-health.md` opens with the answer in prose, with the coverage figures computed live from the committed reports, and the README no longer claims that page shows something it does not.

  The behaviour conversions took the case per suite where a false pass would cost most. Security: a denied tool call leaves no side effect and a durable record, driven through the real `check-tool` path, with a negative control so it cannot pass against an engine that records every call as blocked. Chaos: a policy decision taken before a Postgres outage is byte-identical after recovery, with two probes so a one-directional regression cannot hide. E2E: an exhausted cost budget refuses the next call rather than logging and continuing, using a `costly` tool because that is the only reversibility tier whose decision the budget actually governs.

### Fixed
- **The CI Evaluation Gate stands up a full stack and then bypasses it.** `ci.yml`'s gate provisions Postgres, Redis and a gateway, waits for the gateway to become healthy, and then runs the smoke suite with `--mock`, which skips the control plane entirely. Mock "output" is a fixed four-key dict interpolating the task's own name and description, and mock *context* copies `task.expected` straight back, which is the documented reason `--mock` scored 1.0 while every real run scored 0 (#31). So this gate has been asserting on the mock fixture rather than on the agent or the stack it builds. Surfaced by the rescoped `expected_output_match`: two of three smoke tasks failed a 200-character floor at 190 and 197 characters, purely because their descriptions are short. That is the same defect as a vacuous 1.00, pointing the other way, so the scorer now skips on a mock run and says so, and `mock_context` carries a `mock` marker for scorers to key on. The gate passes again at 3/3 with **assertion coverage 0.5**, which is the honest reading: in mock mode only the policy scorer asserts anything. Removing `--mock` needs model credentials on PR runs and is a cost decision, so it is left as-is and named here rather than changed quietly.
- **The gateway silently dropped every safe-PR eval report before it reached the dashboard ([#7](https://github.com/sattyamjjain/ferrumdeck/issues/7)).** `handlers::evals::parse_stem` only understood `<suite>-<YYYYMMDD>`, the offline-benchmark naming. The LLM-backed suites are written as `eval_<suite>_<YYYYMMDD>_<HHMMSS>`, which contains no hyphen, so `rsplit_once('-')` returned `None` and `load_eval_runs` skipped the file. Silently, because unparseable reports are dropped rather than raising. `/v1/evals/runs` therefore served the offline benchmarks and **nothing at all for the two suites `docs/eval-health.md` is about**, which is the concrete sense in which the eval-health page could not be trusted while its data path was stubbed. The parser now handles both families, `average_score` is recognised as a headline metric, `assertion_coverage` and the run-level task/cost/duration figures are projected through (each one optional and omitted when absent, never a confident zero), and same-day runs order by timestamp so the regression report compares the right pair.
- **The eval-runs read path was wired end to end and still could not render a run ([#7](https://github.com/sattyamjjain/ferrumdeck/issues/7)).** The BFF proxied the gateway body verbatim. The gateway returns `{ run_id, suite, ... }` and the runs table reads `run.id`, `run.suite_name`, `run.status`, so every cell came out blank and `runStatusConfig[run.status]` dereferenced `undefined`. `nextjs/src/lib/evals/run-mapper.ts` now does the projection, drops rows it cannot recognise rather than coercing them, and recomputes the count from what survived so it can never overstate what is shown. Fields the reports genuinely do not record, such as agent version and gate threshold, are left empty rather than invented. A 200 whose body is not a run list now answers 502 rather than rendering an empty table that would read as "no runs have been executed".
- **`tests/chaos` and `tests/e2e` skipped in their entirety, against any stack.** Both conftests probed `/health/live` for readiness; the gateway serves `/health` and `/ready`. The probe never succeeded, so `ensure_services_running` skipped both suites unconditionally, including CHAOS-001, the database-unavailable-fails-closed test, which has consequently never executed despite being described as the one real behavioural chaos test. This is the same bug already fixed in `tests/security/conftest.py` and never propagated. `tests/e2e/conftest.py` carried a second instance: `gateway_client` authenticated with `TENANT_A_KEY`, whose default is not seeded, so every authenticated request would have 401'd even once the probe was fixed. Third occurrence of one pattern, a suite reporting green because it never ran anything.
- **CI collected no tests from the repo root, so 18 regression guards never ran.** `ci.yml` names its pytest paths explicitly — `python/packages/*/tests`, `tests/api`, then `tests/integration tests/security` — and `tests/*.py` matched none of them. The guards covering the generated-doc tooling (`scripts/gen_eval_health.py`, `observability/genai_mapping.py`), which lives outside `python/packages`, therefore passed locally and were skipped in CI; the "Python Tests" check went green without executing them. A regression guard that does not run is not a guard. Root-level `tests/*.py` is now included by glob, so a new root test file is picked up without editing the workflow again: 540 tests collected where 522 ran before. Separately, `eval-health-check` is now a prerequisite of `ci-check`, so `docs/eval-health.md` can no longer drift from the committed reports without failing.
- **`docs/eval-health.md` was built from evidence that is not in the repository.** `evals/reports/*.json` is gitignored, so `collect()` globbing the directory read whatever run output happened to be on the author's disk. ## [0.8.0] - 2026-08-03

### Added
- **The audit chain head is anchored outside the database, so a rewritten tail is now detectable ([#14](https://github.com/sattyamjjain/ferrumdeck/issues/14)).** The hash chain shipped in 0.7.16 catches insertion, deletion, and in-place edits, and the release notes said plainly what it did **not** catch: an actor with DB privileges who rewrites the *entire* tail can forge a self-consistent chain, because they hold every input. Signed head checkpoints close that, up to a stated window. New `rust/crates/fd-audit/src/checkpoint.rs` (pure, no DB/clock/RNG): `CheckpointSigner` signs a `(tenant_id, chain_seq, record_hash, checkpointed_at)` head record with an **Ed25519 key that is not the database's** (so a DB-privileged actor cannot forge a checkpoint), `FileCheckpointSink` appends it to an out-of-band, `fsync`'d NDJSON sink (behind a `CheckpointSink` trait so object storage / a transparency log can be added without touching the crypto), and `verify_against_checkpoints` (+ `AuditRepo::verify_against_checkpoints`) **proves the chain has not been rewritten past the most recent checkpoint and names the checkpoint it verified against** — one hash comparison suffices because a record's `record_hash` transitively commits to its whole prefix. Anything after the last checkpoint keeps the previous (in-chain) guarantee, a missing checkpoint **degrades to that guarantee and says so** (its own `Degraded` verdict, never a silent pass), and the docs say so rather than rounding up to tamper-proof — this is **detection, not prevention**, and only as strong as the sink being genuinely out-of-band and the signing key off-box (a file sink on the DB host is a weak anchor; a robust remote sink + off-host key custody is the remaining hardening, still tracked on #14). Proven by 7 tests (`rust/crates/fd-audit/tests/checkpoint_anchor.rs` + `checkpoint_file_sink.rs`), the load-bearing one being that a **wholesale self-consistent tail rewrite after a checkpoint is DETECTED** (the rewritten chain passes `verify_chain` yet fails `verify_against_checkpoints`). Motivated by **EU AI Act Art. 12/19** record-keeping (applicable **2026-08-02**) and **Colorado SB 26-189**'s 3-year retention floor (from **2027-01-01**).

## [0.7.16] - 2026-08-01

### Added
- **Cryptographic hash-chain over `audit_events` — the audit trail is now tamper-*evident*** ([#8](https://github.com/sattyamjjain/ferrumdeck/issues/8)). Append-only (no repo `UPDATE`/`DELETE` path + the `trg_audit_events_append_only` trigger) stops the ordinary tampering paths, but a privileged DB actor could drop the trigger and rewrite rows undetected. ## [0.7.9] - 2026-07-24

### Added
- **x402-aware pre-call spend gate for autonomous payments** (`fd_policy::x402`): extends the existing per-agent cost budget from token/model spend to **paid-API spend**. When an agent's outbound call hits an [x402](https://x402.org) **HTTP `402 Payment Required`** response, the gate parses the quoted challenge (`X402Challenge` — scheme/asset/network/atomic-amount/decimals, from the real `{x402Version, accepts:[…]}` body shape), **normalizes it to cents** as a first-class cost event (`X402CostEvent`) that folds into the **same `cost_cents` ledger as inference** (so a run's cost slope includes autonomous payments, not just tokens), and checks it against the **remaining** per-agent budget **before** the payment is authorized — reusing the exact `Budget::has_cost_headroom` primitive the R2 reversibility rung already uses for token spend. A quote that would breach the ceiling is **hard-stopped** (`X402GateOutcome::Deny` + exactly one operator alert, mapped to `PolicyDecision::deny`); a quote in an asset with **no known USD peg** is **denied by default** (`DenyUnpriceable` — you cannot check a cents budget against an unpriceable quote), consistent with the crate's deny-by-default posture. Cent normalization is integer, **rounded up** (`⌈atomic·100 / 10^decimals⌉`), so sub-cent dust quotes can't slip the budget. **This never moves money** — it is a gate + cost model, not a wallet: it parses simulated 402 bodies, prices them, and returns an authorize/deny *decision*; signing an `X-PAYMENT` header / broadcasting a transfer lives entirely outside FerrumDeck (`simulate → gate → record`). The paid call rides the existing OTel span alongside token cost via `fd_otel::genai::span_helpers::record_x402_cost` (`ferrumdeck.cost.x402_cents` + `ferrumdeck.x402.asset/scheme/network/decision`, primitive-typed so fd-otel keeps no dependency on the fd-policy domain type). New public API surface: `X402Challenge`, `X402CostEvent`, `X402GateOutcome`, `evaluate_x402_payment`, `X402_ANCHOR` (re-exported from the published `ferrumdeck` umbrella). Runnable, self-verifying demo (exits non-zero if the gate fails to block the over-budget payment): `cargo run -p ferrumdeck --example x402_spend_gate` + [`examples/x402-spend-gate/`](examples/x402-spend-gate/README.md). Tests: 12 fd-policy unit tests (parse/normalize-ceil/authorize/hard-stop-with-overage/boundary/unpriceable-deny/no-cap/apply-to-one-ledger/serde) + 2 fd-otel tests (attr-key contract + span-helper smoke). Anchors (verified live): [x402 Foundation under the Linux Foundation](https://www.linuxfoundation.org/press/linux-foundation-announces-operational-launch-of-x402-foundation-to-standardize-internet-native-payments-for-ai-agents-and-applications) (2026-07-14), [Cloudflare Monetization Gateway on x402](https://blog.cloudflare.com/monetization-gateway/) (2026-07-01), [Databricks Unity AI Gateway](https://www.databricks.com/blog/ai-governance-data-ai-summit-2026-whats-new-unity-ai-gateway) hard spend caps, [FinOps FOCUS 1.4](https://siliconangle.com/2026/06/08/focus-specification-ai-cost-accountability-finopsx/) AI token economics.
- **Reproducible governed-vs-ungoverned benchmark + W3C-trace-context spans** (`fd_evals.governed_benchmark`): quantifies the two numbers no closed platform (Alterion Draco, Microsoft Agent 365, AWS Bedrock AgentCore) publishes — **governance overhead** (added latency/cost) and **% of unsafe tool actions blocked** — on one fixed [safe-PR-agent](evals/agents/safe-pr-agent) workload run twice: with the deny-by-default allowlist + Airlock RASP + cost budget **ON** (governed) and **OFF** (ungoverned). Four unsafe actions are injected, one per enforcement layer (`eval()`/`os.system` RCE write → anti-RCE matcher; raw-IP `http_request` → exfil shield; `delete_repo` → allowlist deny; a 6× runaway `search_code` → budget cap). **Reproduced numbers: governed blocked 4/4 (100%) vs 0/4 ungoverned; added decision latency ≈0.9 µs p50 / ≈8 µs p95; audit overhead +0.36¢ / +720 tokens; and governed cost 54% *less* to run (85.4¢ vs 184¢) because stopping the unsafe + runaway calls saves more than the decisions cost.** Deterministic, offline, no LLM: the workload is fixed, so the blocked set, reasons, and cost/token deltas are byte-stable (golden fixture `governed_benchmark.golden.json`); wall-clock latency is the one machine-dependent figure, measured-and-reported (same honesty posture as the enforcement-latency bench). Tests: 2 Rust integration tests (real-engine block-all-unsafe + per-layer-reason) + 8 Python tests (blocking, overhead, determinism, golden, W3C-traceparent shape). ## [0.7.8] - 2026-07-20

### Added
- **Cross-MCP W3C trace-context correlation — MCP SEP-414** (`fd_otel::trace_context`): the enforcement decision span now joins the *caller's* distributed trace. When a tool-call request carries W3C trace context in `_meta` (the unprefixed `traceparent`/`tracestate`/`baggage` keys SEP-414 reserves), the gateway extracts + strictly validates the `traceparent` (version `00`, 32-hex non-zero trace-id, 16-hex non-zero parent-id, 2-hex flags), **rejects** malformed/all-zero values rather than propagating them, caps `tracestate`/`baggage` to the W3C limits (dropping, not erroring, and recording the drop), and **parents the existing decision span** (`fd_otel::decision::emit_tool_decision_span`) on that remote context — no second telemetry path. The trace-id + sampled flag are persisted on the enforcement decision record (the append-only `audit_events` row: dedicated `trace_id`/`span_id` columns + a `trace_context` object in `details`, plus optional additive `trace_id`/`trace_sampled` on the `fd_audit::AuditEvent` receipts substrate), so an audit query can join a policy decision to its trace. Feature-gated behind the **same** OTel semconv stability opt-in as the GenAI span naming (`OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental`); unset, ferrumdeck ignores `_meta` and starts a root span exactly as before — a pure extension for callers who send nothing. **Honest scope:** this **targets** the 2026-07-28 MCP revision (a *Release Candidate* as of this change) and implements the SEP-414 conventions (SEP status *Final*); it is **not** a conformance claim to an unreleased spec. Tests: 10 fd-otel extraction/validation/capping unit tests (valid propagates + parent context matches; malformed + all-zero rejected; absent → root; oversized tracestate truncated + recorded) + fd-storage persistence tests (trace-id lands on the record; no-`_meta` leaves it trace-free) + fd-audit receipts round-trip. Docs: [`docs/mcp-trace-conformance.md`](docs/mcp-trace-conformance.md) (verbatim SEP-414 + W3C quotes, end-to-end trace tree, explicit does/does-not-guarantee), linked from the README observability section.
